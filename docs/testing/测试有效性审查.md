# 测试有效性审查

[返回测试入口](README.md)。本文核对清单、可疑用例、夹具与对应实现。已修正脱离正式调用链的覆盖、可能误通过的断言和旧会话模型夹具，并补充前台跨日及计算耗时的复查回归。本次又同步独立挑战开关契约：仅单词不再自动补入按压，最后一种挑战不能关闭；相关用例与夹具仅静态核对，未编译或运行。提交 `828006b` 的本地及真机结果见[真机验证](真机验证.md)，不作为当前改动的通过证据。

## 范围与判定口径

| 范围 | 静态核对结果 |
|---|---|
| 本地测试 | 70 个测试类、434 个 `@Test` 方法 |
| 设备测试 | 45 个测试类、269 个 `@Test` 方法，另有 6 个夹具 Java 文件 |
| 清单对应 | 两份分类文档的 115 行测试类与源码数量逐项对应，无漏列测试类 |
| 资源引用 | 测试引用的正式 `R.id` 均能在布局或显式 ID 声明中找到 |
| 禁用与条件执行 | 未发现 `@Ignore`；发现 1 处 `Assume` 条件跳过，另有截图及显式恢复的辅助早退 |
| 深入核对 | 优先级、服务调度、持久化会话/休息、共享夹具、截图条件与当前生产入口 |

上述检查不是编译器、完整调用图或全部方法的逐条证明。类型引用扫描以静态线索定位问题；Manifest 注册的 Activity、XML 创建的 View、通配 import 不能因缺少普通 Java 调用就被当作失效。固定日期、模拟包名及反射本身也不是过时的依据。

## 已修正的覆盖问题

| 问题 | 原有证据与影响 | 当前处理 |
|---|---|---|
| 优先级测试脱离正式入口 | 原 `InterceptionPriorityTest` 调用 `InterceptionPriority.beforeRestoring`；当前 `InterceptionRuntime` 已自行处理休息与新禁用，没有调用该辅助类。原测试通过不能保证运行优先级正确 | 替换为 [RuleEnginePriorityTest](../../app/src/test/java/github/vhoom/zhijian/domain/interception/RuleEnginePriorityTest.java)，直接验证正式规则入口在三档强度下的开始/结束毫秒边界和用量证据缺失分支；会话保留交由设备测试验证 |
| 只检查重试，未确认启动发生 | `ForegroundEvaluationTest.acceptedLaunchWithoutVisibleWindowKeepsChecking` 原先硬编码全局版本和修心档位，只断言 Handler 有后续任务；请求因配置不匹配而提前退出也会安排重试 | 使用当前提交快照构造有效请求，先断言记录到 `startActivity` 的 Intent 与会话，再断言后续检查 |
| 旧结果拒绝用例缺少有效阻断输入 | 旧访问用例传入不含持久会话的纯规则结果；销毁用例传入允许结果，难以直接验证“晚到禁用不能启动页面” | 两者改为携带完整会话的阻断结果，并明确断言没有启动 Intent；保留队列行为断言 |
| 设备优先级夹具使用旧会话模型 | 原夹具只调用 `PendingInterceptionStore.save`，没有调用当前独立的 `saveRest`，也没有准备相应周期；还要求跨组员旧展示被清空 | [InterceptionPriorityRuntimeTest](../../app/src/androidTest/java/github/vhoom/zhijian/runtime/interception/InterceptionPriorityRuntimeTest.java) 分别建立周期、休息和展示，验证新禁用及独立限制已保存，原休息身份、发生时间和周期键仍保留 |
| 测试组限制清理不完整 | `PendingInterceptionStore.clear` 不删除 `restriction-block:`；原两个测试类只清展示后删除组，可能残留限制并影响闭关配置恢复 | 前台共享组用例与优先级设备用例按本次组身份清理独立限制，再清会话；优先级用例另清自身周期 |
| 依赖环境档位及初始化顺序 | 共享组路由原先始终要求直接启动，但正式 `redirectSharedPending` 在闭关时返回复查；部分服务用例没有统一等待快照初始化 | [ForegroundEvaluationTest](../../app/src/androidTest/java/github/vhoom/zhijian/accessibility/ForegroundEvaluationTest.java) 明确区分闭关复查与交互档位重定向，并在测试线程的 `@Before` 等待存储就绪 |
| 夹具异常打断恢复 | 正式服务夹具的 close 曾在第一个错误后停止；分组设备会话在构造期间先改状态，构造失败时不会自动进入 try-with-resources 的 close | 两个会话接入 [FixtureCleanup](../../app/src/androidTest/java/github/vhoom/zhijian/fixture/FixtureCleanup.java)，修改前注册、初始化失败立即回滚、逐项恢复与异常汇总；组在保存前登记，单条事实和各配置独立清理 |
| 前台复查缺少午夜与实际耗时边界 | 当天无规则的允许结果最长等待一分钟，可能错过下一星期规则生效；后台计算耗时未从原复查间隔扣除 | [InterceptionEvaluationTest](../../app/src/test/java/github/vhoom/zhijian/domain/interception/InterceptionEvaluationTest.java) 的 5 个用例验证星期规则切换和期限计算；服务用例另检查 4 种真实 Handler 排队结果，覆盖午夜、延迟回调以及期限已经过去的情况 |
| 服务测试构造不合法的单成员组 | 真机运行时 `GroupedInterceptionServiceTest` 保存组失败；当前规则要求至少两个不同成员 | 增加第二个逻辑测试成员，保留同一真实成员持续前台的服务断言；组和周期在保存前登记清理，本用例不宣称覆盖两个应用的切换 |
| 按压结束时重新查找已移除控件 | `RepairContinuationTest` 的短按压完成后进入反问页，再按 ID 查找原按钮发送抬起事件会发生空指针 | 保留按下时的 View，并使用同一手势开始时间向该实例发送抬起事件 |
| 挑战候选与正式策略不一致 | 提交 `828006b` 前的策略强制包含按压，原测试误以为能够关闭；当前策略改为保留最后一种挑战 | 正式服务用例继续按实际启用集合查找种子；独立开关用例覆盖仅单词及仅按压，不再断言按压始终开启 |
| 最后一项保护影响测试恢复与空配置输入 | 按枚举顺序逐个恢复可能先尝试关闭最后一项；通过正常 API 已无法构造空配置 | 恢复时先开启原选择再关闭其他项；重入用例在服务连接前注入异常空偏好，保留对恢复入口的验证 |

生产依据为 [InterceptionRuntime.evaluate / present](../../app/src/main/java/github/vhoom/zhijian/runtime/interception/InterceptionRuntime.java)、[ZhijianAccessibilityService](../../app/src/main/java/github/vhoom/zhijian/accessibility/ZhijianAccessibilityService.java)、[PendingInterceptionStore.save / saveRest / clearSession / clearBlock](../../app/src/main/java/github/vhoom/zhijian/data/store/interception/PendingInterceptionStore.java)。前台服务在运行规则前记录墙上时钟和单调时钟，回到主线程后通过 [InterceptionEvaluation.recheckDelayMs](../../app/src/main/java/github/vhoom/zhijian/domain/interception/InterceptionEvaluation.java) 计算尚余等待时间；午夜取本轮计算所在日期的结束边界，已经到期返回 1 毫秒复查，仍保留服务原有的较早任务优先规则。

原 [InterceptionPriority](../../app/src/main/java/github/vhoom/zhijian/domain/interception/InterceptionPriority.java) 辅助类仍在生产目录中；当前未发现生产调用者，本次仅更换测试依赖，不以它作为运行链路覆盖的依据。

## 设备夹具恢复的当前实现

- `FixtureCleanup.initialize` 包装可能部分修改状态的初始化。失败时立即运行恢复计划，保留原始异常，并把恢复错误附加到 suppressed 链。
- `close` 尝试全部已登记步骤；异常与断言错误都不会跳过后续步骤。第一次关闭完成后，重复关闭不重复写设备状态。
- `ProtectionDeviceSession` 将窗口退出、系统设置、通行证、单条事实、各设置项、测试应用周期和监听器拆为独立步骤；仅构造而未启动时只释放监听器。测试应用周期清理由本次真机结束后的存储比对发现遗漏后补齐。
- 分组会话在构造中的第一次授权修改前登记恢复计划；每个组在调用保存前加入清理清单，组限制、组配置和周期分别尝试清理。
- [FixtureCleanupTest](../../app/src/androidTest/java/github/vhoom/zhijian/fixture/FixtureCleanupTest.java) 的 5 个内存故障注入用例已在真机通过。它们验证恢复协调器，Android 系统授权和持久化恢复另通过真实会话及测试前后状态比对核对。

## 当前验证的限制

- 设备仅验证本次选定的 6 类，不能推断其余 229 个设备方法通过。已有用户限制使一个闭关返回用例条件跳过，没有清除用户限制来强行运行。
- 真实前台、系统 UsageEvents、固定时间等待、厂商 ROM 和主线程调度仍可能影响设备用例。本次单台 Android 11 设备的分批结果不能作为稳定性、性能或其他系统版本的通过率数据。
- 两个设备会话已处理普通 Java 异常导致的恢复中断，本次运行后核对了设备授权和原有策略。进程强制终止时无法保证执行清理；系统拒绝操作或恢复动作本身失败时，也不能保证对应设备状态恢复成功。队列会尝试其余动作并报告恢复错误。
- Room 与 SharedPreferences 的跨存储恢复没有进行进程崩溃注入；预览、组件布局及截图也没有进行视觉验收。

这些限制不等于所有相关测试无效；它们说明结果应该在哪个范围内解释。设备用例应在独立测试环境执行，条件不满足与清理异常应明确报告。
