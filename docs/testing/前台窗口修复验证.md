# 前台窗口修复验证

验证分支为 `bug/fix-time-rule`，被测业务提交为 `c27671a`。该提交修复键盘、浮层和异步前台核实导致的重复拦截。本次经用户确认修正本地及设备测试，并验证挑战页静止和实际操作均累计休息；当前业务实现已符合该要求，未追加修改业务代码。

## 用户操作、Bug 逻辑与修复后逻辑

| 用户操作 | Bug 逻辑 | 修复后逻辑 |
| --- | --- | --- |
| 在随心模式点击继续，或在修心模式完成挑战并继续，然后在原应用打开、收起输入法 | 原过滤器根据应用是否有启动图标判断浮层。搜狗等带图标的输入法被当成切到另一应用，清除了本次继续确认；返回原应用时，同一禁用再次弹页。 | 先检查窗口类及系统组件声明。明确的键盘窗口不改变前台访问身份，不清除继续确认，收起键盘后继续使用原应用。 |
| 留在原应用时，另一个带图标的应用出现弹窗或浮层 | 原逻辑只看到另一包名就判定离开，没有证明底下的前台应用已经变化。 | 不是明确 Activity 的窗口先后台核实系统前台；实际前台仍是原应用时，保留原访问确认。 |
| 从键盘进入输入法设置，或返回桌面、切到其他应用 | 若把输入法整个包永久排除，会把输入法自己的设置页面也误认为键盘，无法正确结束原访问。 | 输入法设置 Activity 属于真正的页面切换。桌面、其他应用的真实前台同样结束原访问；之后返回原应用重新检查禁用。 |
| 模糊窗口核实还未结束时，快速切到另一应用 | 旧后台核实结果可能晚到，把新前台改回旧包名；旧规则计算结果也可能在身份未确定时再次弹页。 | 核实回调必须匹配当前窗口代次。新事件使旧回调失效；等待核实期间延后规则检查和弹页，避免展示旧结果。 |
| 输入法连续发送大量窗口通知 | 重复通知若不断重启核实或重建访问，会拖延核实及提醒，也会误改访问身份。 | 同一模糊窗口合并为一次核实；明确键盘不重建访问，不推迟既有连续提醒期限。 |
| 系统前台证据读取失败 | 仅凭陌生窗口包名推测离开，会误清除已保存确认。 | 保留原确认并安排复查。读取失败不被解释为真正离开。 |
| 要求休息30秒，进入挑战页后先静止等待，再按压、答单词或填数独 | 若把挑战操作当作受管控应用使用，会重置休息；若完成挑战另开计时，则会让用户重复休息。 | 当前实现已经将止间挑战页排除在使用范围外。静止、实际操作和完成后停留连续累计同一次休息，不增加受管控应用用量，不重置休息身份。提前回到受管控应用才打断未满的休息；挑战与休息分别判断，最终继续仍遵循会话流程。 |
| 同时达到限时、限次等禁用，继续后仍留在同一应用 | 旧单元用例仍要求“只跳过单条禁用”，与此前已实现的本次访问确认规则冲突，因此本轮出现三个测试失败。 | 同应用、同档位、同策略版本的一次访问跳过全部禁用；连续提醒独立生效。跨应用、跨档位、跨策略或配置版本变化仍重新判定，真实用量不清零。 |
| 已确认一次提醒，将使用阈值从15分钟调到1分钟，或从1分钟调到15分钟 | 若最终展示仍使用旧阈值，会在调小后漏提醒、调大后提前提醒。 | 正式提交后按新阈值计算确认以来的新增用量，同组另一成员采用相同边界；累计用量及原未完成休息保留。 |
| 旧提醒已继续，修改同一提醒窗口的起止时间，新窗口也达到使用阈值 | 旧确认若抵扣新窗口用量或旧展示遮挡新提醒，会漏掉新窗口的首次提醒。测试原来仅保存旧提醒而未同步旧周期，造成零用量旧周期被判为已休息。 | 旧休息保留，新窗口独立统计及提醒。用例现在同时准备旧提醒和匹配的旧周期，验证配置提交后以及新窗口展示后都保留旧休息。 |

输入法问题的原始诊断证据见[时段规则修复核对](时段规则修复核对.md)：继续确认已应用后，输入法被记录为前台，随后原应用再次命中同一时段禁用。修复不读取键盘内容或用户输入。

## 已修正的测试问题

- 数独夹具原来等待第一个格子可编辑，但给定格按正式规则不可编辑。现在等待完整题面中任意可填写格就绪，之后通过真实格子及数字键完成题目；三种挑战与反问开关组合的正式继续回归已通过。
- 挑战完成后重进用例原来要求隐藏的 `interception_countdown` 可见。现在核对正式运行入口仍返回未完成休息、重新要求完整连续休息、展示及休息身份保留、无通行证且页面继续拦截；回归已通过。
- 分组全天限时、时段限时及全天限次用例原来以启用前历史设置额度，与正式运行入口的统计起点不同。现在从成功保存后的起点检查两成员各自不足12秒、合计达到12秒触发拦截；限次用例允许前两次打开、第三次触发，并断言实际次数为3。这三个真实UsageEvents回归已通过。
- 本地确认用例更新为本次访问全部禁用共同放行，并保留跨应用、策略、档位和版本隔离、提醒期限及真实用量断言。
- 提醒端点更替用例原来只保存旧提醒，未同步其已达到阈值的旧周期；配置结算得到零用量旧周期，运行入口按已休息完成清理它。现在在提交新参数前同时保存匹配统计身份及代次的旧周期，保留提交后及新窗口展示后的旧休息断言。全天、时段及更替窗口共4个方法全部通过。

新增的设备方法在30秒休息要求下分别打开按压、单词、数独正式挑战页，等待静止时间、完成实际挑战并停留，再读取正式周期存储，核对使用量不增加、休息随真实经过时间累计、同一休息身份不变且无临时通行证。另有两个本地方法验证挑战页交接不中断休息、回组打断及静止足额休息完成。

65个设备回归执行前，无障碍服务列表为`null`、总开关为`0`、使用访问为默认模式，执行后已恢复。用户随后开启了止间无障碍和使用访问，本次4个补测前记录为止间服务组件、总开关`1`、使用访问`allow`；测试后按该次初始状态恢复，保留用户后来开启的授权。规则与挑战设置由各自夹具恢复，本次未另做全量数据库前后比较。

## 证据与验证边界

本地报告位于`app/build/reports/tests/testDebugUnitTest/index.html`，默认设备报告位于`app/build/reports/androidTests/connected/debug/index.html`；65个设备结果及4个补测结果分别保留在`app/build/validation/foreground-window/core-device-results.xml`和`threshold-device-results.xml`，Lint报告位于`app/build/reports/lint-results-debug.html`。以上为本次执行生成的忽略目录产物，未纳入版本控制；重新运行相同任务会覆盖默认报告。

提醒阈值设备用例通过正式配置提交及运行入口验证，周期用量由夹具可控准备；它们没有实际等待1分钟或15分钟，不能替代全部真实使用时序场景。

新增的 10 个窗口回归在实际 Android 运行时调用正式服务事件入口并读取独立偏好，但组件查询及系统前台回调采用可控输入。它们验证代码分支、确认持久化和竞争保护，不能替代搜狗等厂商输入法的手动验收。未运行其余设备测试，未验证完整厂商窗口延迟、保存中系统回收、Android 16 大屏方向或全部昼夜主题场景。
