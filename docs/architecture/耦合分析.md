# 耦合分析与扩展边界

依赖分析以 `620ffc2` 为基线，类型、线程名称与源码路径跟随当前工作区，范围见[索引](README.md)。本文分别记录已经存在的依赖与状态约束、它们对维护的影响，以及后续可选择的改进方向；本次仅统一项目命名。

## 总体判断

项目已经把规则计算、交互流程、Android 用量读取和页面组件分开，但仍有三类明显耦合：包之间的反向引用、跨存储的会话状态、集中在运行和 Activity 中的协调逻辑。优先理解这些边界，比仅按目录拆成多个 Gradle 模块更有用。

尤其要区分“状态协作形成闭环”与“源码包存在依赖环”：页面保存影响下一次评估是正常业务反馈；领域参数绑定到存储实现所在包，则会直接限制代码的独立复用。

## 已确认的包依赖与反向引用

| 位置 | 当前代码证据 | 维护影响 |
|---|---|---|
| `data.store ↔ domain.interception` | [ZhijianStorage](../../app/src/main/java/github/vhoom/zhijian/data/store/ZhijianStorage.java) 调用 `RetreatChangePolicy.requireAllowed`；[RetreatChangePolicy](../../app/src/main/java/github/vhoom/zhijian/domain/interception/RetreatChangePolicy.java) 的参数是 `data.store.PolicySnapshot` | 静心规则依赖具体快照类型；快照还负责从 DAO 加载，领域入口与存储组织绑定 |
| `data.model.runtime ↔ domain.interception` | [PendingInterception](../../app/src/main/java/github/vhoom/zhijian/data/model/runtime/PendingInterception.java) 和 [BlockContinuation](../../app/src/main/java/github/vhoom/zhijian/data/model/runtime/BlockContinuation.java) 引用 `InterceptionDecision`；[InterceptionEvaluation](../../app/src/main/java/github/vhoom/zhijian/domain/interception/InterceptionEvaluation.java)、提醒及重入规则反向引用 `PendingInterception` | 判定与会话模型分居两包，移动其中一类会影响规则计算、持久化和页面协议 |
| `data.store ↔ data.source` | `ZhijianStorage` 创建 `ContinuousUsageReader`、`ReminderUsageReader`、`RetreatProtectionReader`；[ContinuousUsageReader](../../app/src/main/java/github/vhoom/zhijian/data/source/ContinuousUsageReader.java) 默认从 `ZhijianStorage` 取快照和检查点 | 数据源并非全是无状态读适配器；部分同时协调周期持久化与配置有效性 |
| `util.permission ↔ accessibility` | [PermissionStatusReader](../../app/src/main/java/github/vhoom/zhijian/util/permission/PermissionStatusReader.java) 使用 `ZhijianAccessibilityService.class`、`AccessibilityConnection`；[ZhijianAccessibilityService](../../app/src/main/java/github/vhoom/zhijian/accessibility/ZhijianAccessibilityService.java) 又调用权限读取 | 权限工具与具体服务绑定；将整个 `util` 视为底层通用库会掩盖这个环 |
| 用量模型 → 系统读取包 | [DailyUsage.of](../../app/src/main/java/github/vhoom/zhijian/data/model/usage/DailyUsage.java) 接受 `UsageStatsReader.Snapshot` | 展示模型的数据转换绑定到具体 Reader 的嵌套类型；更换数据源时可能牵动模型 API |
| 页面 → 运行层与持久化 | [InterceptionActivity](../../app/src/main/java/github/vhoom/zhijian/ui/interception/InterceptionActivity.java) 直接使用恢复运行器，创建结果写入器；[InterceptionOutcomeWriter](../../app/src/main/java/github/vhoom/zhijian/ui/interception/session/InterceptionOutcomeWriter.java) 协调多个 Store | 生命周期、运行复查和完成业务仍由 UI 包承接；它不只是 View 渲染层 |

前四行是包级双向引用的具体证据。包级聚合会把不同类合并成一个节点，不能据此断言所有类都存在直接循环，也不能据此判断运行时死锁。

## 修改影响较广的类型

下表统计被多少个不同正式源码文件显式导入，同文件重复或内部类型引用按文件去重；未计同包使用与全限定使用。

| 类型 | 导入文件数 | 评估改动时应联看的范围 |
|---|---:|---|
| `RuleGroup` | 26 | 编辑草稿、验证、逐日配置、编码、规则计算、统计范围 |
| `ControlLevel` | 25 | 强度设置、流程选择、静心保护、会话与确认身份 |
| `PendingInterception` | 17 | 运行恢复、提醒休息、页面请求、偏好持久化 |
| `InterceptionDecision` | 15 | 判定、页面流程、审计结果、访问确认 |
| `AppConfig` | 12 | 资源默认值、输入配置与运行默认参数 |
| `ZhijianStorage` | 10 | 启动就绪、配置写入、快照读取、业务 Store 和系统读取 |

这些数字表示共享程度。`RuleGroup`、`ControlLevel` 被广泛使用有业务原因，不应为了降低数字而复制模型。需要重点控制的是共享类型是否混入 UI、Android 或存储职责，以及调用者能否修改其内部状态。

协调职责主要集中在以下位置：

- `ZhijianStorage` 同时处理数据库生命周期、队列、默认组初始化、词库就绪、配置事务、静心变更限制和快照发布。它是装配与提交边界，不宜继续加入页面流程。
- `InterceptionRuntime.evaluate()` 处理遗留休息、通行证、用量、访问确认、当前规则和展示恢复，规则判断本身已经下沉到 `RuleEngine`。新增规则应先检查是否能在现有计算入口完成。
- `InterceptionActivity` 包含请求重入、状态恢复、预览、计时、规则复查、页面构造和异步完成。页面工厂已经拆开 View，但生命周期协调仍集中于 Activity。

## 状态、身份与时间耦合

| 状态边界 | 当前实现 | 必须一起理解的约束 |
|---|---|---|
| 已提交配置与运行状态 | [ZhijianStorage.State](../../app/src/main/java/github/vhoom/zhijian/data/store/ZhijianStorage.java) 汇集 `PolicySnapshot`、`RuntimeSnapshot` 和词库，使用 `volatile state` 发布 | 配置事务成功后才发布新快照；调用 `state()` 前必须完成初始化 |
| 可变草稿与有效策略 | [PolicySnapshot](../../app/src/main/java/github/vhoom/zhijian/data/store/PolicySnapshot.java) 对外返回 `RuleGroup` 副本；保存入口也复制草稿 | 不能把编辑中的 `RuleGroup` 直接当作已提交状态共享给评估器 |
| 策略归属 | `effectivePolicyId`、`revisionOf`、`usageScopeFor` | 应用覆盖、组归属或规则版本变化，都会改变会话有效性和用量范围 |
| 前台评估结果 | 服务保存 `foregroundVersion`、`evaluationVersion`，页面保存请求和恢复代次 | 旧异步结果必须匹配当前目标与代次；相同包名不代表仍是同一次请求 |
| 展示与休息 | [PendingInterceptionStore](../../app/src/main/java/github/vhoom/zhijian/data/store/interception/PendingInterceptionStore.java) 区分展示记录、`reminder-rest:`、`restriction-block:` | 清理展示不等于取消未完成休息；清理接口和会话身份不能混用 |
| 本次访问确认 | [BlockContinuationStore.ignore / readForVisit](../../app/src/main/java/github/vhoom/zhijian/data/store/interception/BlockContinuationStore.java) | 绑定应用、策略版本、档位、触发类型、窗口、启动身份及确认时间；不能扩展为整组永久放行 |
| 运行计时 | [PassGrant](../../app/src/main/java/github/vhoom/zhijian/data/model/runtime/PassGrant.java)、[ContinuousUsageCycle](../../app/src/main/java/github/vhoom/zhijian/domain/usage/ContinuousUsageCycle.java)、[BootIdentity](../../app/src/main/java/github/vhoom/zhijian/util/time/BootIdentity.java) | 墙钟、单调时钟和启动身份共同参与恢复；不能仅凭墙钟差值延续上次启动的计时 |

当前 `BlockContinuation.startedAtMs` 保存的是本次点击继续的确认时间。旧拦截的 `occurredAtMs` 保留触发事实；两者不能互换，否则确认之前发生的离开与重进会被误判为新的访问。每条确认独立查询此后的重入证据。

页面完成时使用本会话的交互设置。以后修改临时放行或挑战开关，不应让旧页面以新选项解释已经发生的交互。相关入口为 [InteractionSessionState](../../app/src/main/java/github/vhoom/zhijian/ui/interception/session/InteractionSessionState.java)、`InterceptionActivity.loadRequest()` 与结果写入器。

## 线程和锁的协作

| 执行位置 | 实现职责 | 扩展约束 |
|---|---|---|
| Android 主线程与 Handler | 服务调度、窗口启动、页面生命周期、UI 回调 | 不把用量查询或数据库等待移到此处 |
| `zhijian-interception` 单线程执行器 | 服务前台记录与规则评估 | 运行层内部存在 `join()`，调用环境必须允许后台等待 |
| `zhijian-storage` 单线程队列 | 初始化、业务写入和快照刷新；容量 128 | 保持事务与快照发布顺序，不绕开队列并发改数据库 |
| `zhijian-storage-read` 读取队列 | 就绪后的查询；2 个线程、容量 64 | 返回结果仍需要调用者判断页面或请求是否过期 |
| `zhijian-usage-archive` 执行器 | 归档系统数据读取、合并未完成请求 | 与拦截评估队列分开，但最后仍经过存储入口 |
| `ContinuousUsageReader` 静态周期锁 | 周期推进、配置变更、展示保存和访问确认的部分关键区 | 是多个组件共享的同步边界，不是单个 Reader 实例锁 |

队列实现见 [TaskQueue](../../app/src/main/java/github/vhoom/zhijian/util/concurrent/TaskQueue.java)。页面恢复另通过 `CompletableFuture.supplyAsync` 执行，不能假定所有运行评估都串行发生在服务的执行器上。

周期锁内目前包含部分系统用量查询或同步持久化操作，这是需要留意的锁作用域，未测量其实际耗时。后续变更不要在持锁线程等待另一项也必须获取同锁的任务。

`BlockContinuationStore.readForVisit()` 已把重入证据读取放到自身偏好锁之外，再按原记录身份清理过期确认。扩大锁范围或改为无条件清空，会破坏对并发新确认的保护。

## 跨存储提交与恢复

结果保存包含 Room 事务和之后的偏好更新：

```text
Room：审计记录 + 可选通行证
  → 刷新运行快照
  → SharedPreferences：确认访问、确认提醒或清理展示
  → 页面完成导航
```

[RuntimeStateStore.recordInterception](../../app/src/main/java/github/vhoom/zhijian/data/store/RuntimeStateStore.java) 负责第一段事务；[InterceptionOutcomeWriter](../../app/src/main/java/github/vhoom/zhijian/ui/interception/session/InterceptionOutcomeWriter.java) 串联后续步骤。进程可能在两段之间退出，所以这不是跨 Room 与偏好的原子事务。

当前保护包括：运行层查询已允许的会话记录；展示前检查有效通行证或访问确认；结果写入后重新核对当前展示会话；清理按会话或原记录身份进行。由此只能说明代码具有对应恢复和防过期措施，不能从静态阅读推断任意崩溃点都已验证。

添加新的完成效果时，应同时检查“审计已写、偏好未写”“新页面替换旧页面”“保存回调晚到”三个路径，而不是只修改页面按钮回调。

| 已有机制 | 源码入口 | 适合继续扩展的方向 |

| 流程策略与状态转换 | [ModeFlowPlan](../../app/src/main/java/github/vhoom/zhijian/domain/interception/ModeFlowPlan.java)、[InterceptionFlow](../../app/src/main/java/github/vhoom/zhijian/domain/interception/InterceptionFlow.java) | 在领域层描述页面顺序与完成效果，避免散落到每个 View |
| 系统事件适配 | [UsageEventTimeline](../../app/src/main/java/github/vhoom/zhijian/data/source/UsageEventTimeline.java) | 将平台事件转为领域时间轴，领域计算继续使用普通数据 |
| 缓存代理职责与可注入数据源 | [CachedAppCatalog](../../app/src/main/java/github/vhoom/zhijian/data/source/CachedAppCatalog.java) | 通过缓存接口与 `Supplier` 替换扫描源，保留快照发布语义 |
| 观察者 | [AccessibilityConnection](../../app/src/main/java/github/vhoom/zhijian/accessibility/AccessibilityConnection.java)、[PermissionStatusObserver](../../app/src/main/java/github/vhoom/zhijian/util/permission/PermissionStatusObserver.java) | 使用成对的订阅与解除订阅，保持页面生命周期内的连接观察 |

当前 `RuleEngine` 是集中汇总规则、调用次数评估器并处理优先级的实现，不能仅凭执行顺序称为已实现独立的 GoF 责任链。新增抽象应解决实际扩展点。

以下是后续建议，均未在本次实现：

1. 先梳理共享类型归属。让静心规则依赖只读策略视图或明确的输入数据，将 DAO 装载保留在存储适配端；一起评估 `InterceptionDecision` 与会话模型的包边界，避免仅移动单个文件造成新反向引用。
2. 缩小权限工具对具体服务类的依赖。可把服务身份和连接状态放到明确的 Android 集成边界；普通格式、时间与并发工具继续独立。
3. 若拦截完成流程继续增长，将结果保存与恢复协调收敛到运行层的应用服务，Activity 只传入会话命令并接收结果。保留现有会话校验、失败恢复和持久化顺序。
4. 新规则优先复用 `RuleEngine`、`CountRuleEvaluator`、`RuleParameterFactory` 等现有入口；规则种类增长到确需独立实现时，再引入评估策略或责任链，并显式保留禁用与提醒的优先级。
5. 有独立构建、复用或团队边界需求时，再评估 Gradle 拆分。拆分之前先消除目标边界上的包依赖环，不能直接把当前六个目录各变成模块。
